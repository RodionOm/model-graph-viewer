## Архитектура

Поток данных:

```text
OpenVINO XML + BIN
        |
        v
OpenVINOLoader --> Graph --> Pipeline --> GraphvizRenderer --> SVG
                               ^
                               |
                    Highlight / HideConstants

Python API управляет этим процессом.
CLI проверяет аргументы и вызывает тот же API.
```

Предлагаемая структура, которую можно уточнять без изменения контрактов:

Это целевая структура, а не требование создавать пустые модули заранее. Разделять код по ответственности по мере реализации.

Основной стек: Python, OpenVINO, Python-пакет `graphviz`, отдельный установленный Graphviz с `dot`, pytest. Версии зафиксировать после проверки совместимости в чистом окружении. Экспорт TinyLlama вынести в отдельный набор зависимостей, чтобы обычная установка viewer не требовала всего стека экспорта.

OpenVINO импортируется в загрузчике. Граф, passes и renderer не получают объекты OpenVINO. API и CLI не дублируют логику.

## Контракты данных

### Узлы и связи

- `Node`: уникальный `id`, отдельное `name`, `op_type`, атрибуты операции, сведения о доступных портах и отдельные метаданные визуализации.
- `Edge`: ID источника, индекс выходного порта, ID назначения, индекс входного порта, доступные форма и тип тензора.
- Узлы хранить по ID. Имена не использовать как ключ идентичности.
- Граф поддерживает несколько рёбер между одной парой узлов. Ключом связи не может быть только пара `(source, target)`.
- Разрешён fan-out одного выхода на несколько входов, в том числе разные входы одного узла.
- Для графа операций один входной порт имеет не более одного источника. Разные входные порты одного узла сохраняются отдельно.
- Индексы портов не перенумеровывать при удалении соседних связей.
- Отдельно хранить входные и выходные порты узла: порт может существовать без видимого ребра после преобразования.
- Атрибуты операции и добавленные визуальные данные не должны перезаписывать друг друга.

Для частых обращений использовать индексы входящих и исходящих связей. Централизовать изменение графа в методах, которые обновляют эти индексы. Цель для загрузки и базовых passes — время порядка `O(V + E)` без повторного сканирования всех рёбер для каждого узла.

### Формы и типы

Различать скалярную форму `()`, известный ранг с динамическими размерностями, динамический ранг и отсутствующую информацию о форме. Не заменять все эти случаи пустым tuple.

Предлагаемый небольшой контракт: `shape=None` означает отсутствие метаданных; отдельный объект формы с `dimensions=None` означает динамический ранг; tuple размерностей представляет известный ранг. Размерность сохраняет статическое значение, неизвестное значение или интервал. Окончательное представление выбрать на этапе реализации графа, проверить round-trip из доступной информации OpenVINO.

Тип тензора хранить независимо от OpenVINO; отсутствующий тип обозначать явно. В renderer иметь единый форматтер, например `fp32[?, 768]`, `fp32[]` для скаляра и отдельную запись для неизвестного ранга. Не обращаться к статической форме там, где модель допускает динамическую.

### Владение данными и валидация

Загрузчик создаёт новый граф с обычными Python-данными, без ссылок на исходные операции и буферы весов. Passes изменяют этот граф на месте; это явно документируется. Для before/after рендерить исходный граф до преобразований либо делать одну осознанную копию. Не копировать весь граф на каждом pass.

`validate()` проверяет уникальность ID, наличие концов рёбер, корректность портов, согласованность индексов и отсутствие конфликтующих источников одного входа. Удаление узла не оставляет висячих рёбер. Проверки запускать на границах этапов и в тестах; избегать полного обхода графа после каждой вставки.

Валидность визуального графа не требует, чтобы после скрытия констант каждый вход по-прежнему имел видимое ребро.
